## Context

R-INT-2 and R-INT-4 ask for one contract through which any external backlog can be read and written, and R-INT-3 asks that AI agents update the backlog through the same guardrails as the UI. The first adapter is this repository's own backlog, kept as files under [`.vault/`](../../.vault/README.md): one Markdown file per item with YAML front-matter, where the directory an item sits in is its status, and where every write goes through the format's reference tooling, which rewrites the front-matter, moves the file and stamps the sprint as one step. VEC-53 and VEC-57 delivered the read side: a `BacklogSource` extension point returning a full snapshot, a status model of three categories with an outcome on end states, and an idempotent import by upsert on `(workspace_id, key)` under a per-workspace advisory lock. The questions left open were whether Vectis is the system of record or a projection, how a Vectis edit reaches the files and what happens on conflict, how identity is reconciled when two sources share a key, whether binding a repository of backlogs means watching or reconciling, what vocabulary the SPI needs beyond a snapshot, and where the agent surface sits.

The forces: the files are authoritative by the operating model's own rule and must stay so; many agents and people write concurrently, so every writer faces read-after-write, write-after-write and write-after-read hazards; the extension SPI is framework-free; the service runs in a native image on a read-only root filesystem; the repository is public, so the format's writer must be public too; and an agent surface must not become a way around the authenticated API.

## Decision

1. **Vectis is a reconciling projection over the canonical files, never a second system of record.** The database is rebuilt from content identity: per item it keeps the source, the path, the blob hash and the revision it was derived at, never a modification time. A file that fails validation keeps its last good row, with the problem attached. A row whose pending write no longer matches the files shows `OUT_OF_SYNC` with the revision it was derived at; it is never healed by the database. Rows are tombstoned only when their inventory entry vanished from a complete snapshot. A continuous-integration test asserts that a full re-list at any commit regenerates identical rows and that the second run appends zero events. When the database and the files disagree, the files win, because the database has no standing to disagree.

2. **Write-back is a command replayed through the format's reference writer, never a merge of text.** A mutation on a file-backed item records, in the transaction that bumps `item.version` and appends the workspace event, a command carrying the item key, the base commit, the base blob hash, the field deltas, the principal, the actor, the channel and an idempotency key, and flags the row pending; clients see the pending state over SSE. One worker per workspace drains commands in order under the workspace's advisory lock; a failing command parks without blocking the queue. The worker checks out the backlog at the base commit, applies the deltas through the writer's own commands, commits with a message carrying the item ids and the cross-reference, and pushes with a lease on the base commit. The row settles only when the reconcile loop observes the pushed blob, which is how the echo of a write-back is recognised without a special channel. On a non-fast-forward the worker fetches and retries only if the item's blob is unchanged at the new head; otherwise it reconciles field by field.

3. **Concurrent edits are data hazards and receive the canonical solutions, consistently at every writer.** Versioning is the renaming, the version check is the interlock, the per-workspace queue is the commit order, the pending state over SSE is the forwarding, and a stale command is replayed against the new base. A field changed on both sides is detected by version and resolved by refuse-and-replay, never by priority and never by wall-clock last-writer-wins. Ownership removes a class of conflicts: status, directory, sprint stamps, completion date, delivery credit and id belong to the writer, so a Vectis command asks for a transition and the writer decides; body sections, comments and links append; existence belongs to the files, so Vectis never deletes a file, and a delete is a crosswalk tombstone plus a notification. The same base precondition applies to the writer's own commands, so the client, the agent surface and the command line share one interlock.

4. **The format's writer is promoted to the public framework and runs beside the service.** Its behaviour is the format's only specification, so a second implementation in Java is refused. In development the writer runs as a local process over a checkout; in Kubernetes it runs as a sidecar that owns the checkout and the push credentials and takes commands over localhost. Vectis talks to a `VaultWriter` port, and push credentials never enter the service container. Until the writer is public, file-backed workspaces are read-only and the client says so on imported items. The first write-back increment covers status, sprint membership and estimates, the commands the writer already has; title and body follow a field-setting command.

5. **Identity is a crosswalk; the display key is never the identity.** Every row carries `(workspace_id, source_id, key, item_id, path, blob_sha)`. The existing `unique (workspace_id, key)` stays; the UUIDv7 is the identity across re-keying (R-CORE-6), and a new key adds a crosswalk row and keeps the old one as an alias. Two sources that both use a key bind to two workspaces and never meet. Two files claiming one key inside a source keep VEC-53's rule for a stale copy after a move and otherwise produce a conflicted row that keeps the path it was derived from, never a silent drop. **Vectis never mints a key for a file-backed workspace**: creating an item there is a command the writer fulfils with its serialised, committed counter (the id is committed on the main branch before it is used). No renumbering repair is built: prevention is the committed counter as the policy of every space, this repository's `.vault/` copy included; detection is the format's gate on every push; a duplicate that enters through a merge of two histories is repaired by a documented manual step.

6. **A binding implies a level-triggered reconcile on a jittered timer; every watcher, hook and webhook is a hint.** The binding is a list of `{space, path}` rows, one workspace per space, provisioned by reference from the Scrum template with the Refined delta. The reconcile runs every 60 s ± 25 % (30 s on a local checkout), returns at once when the generation token equals the last one, diffs blob hashes, upserts and tombstones only changed items under the advisory lock taken with the `try` variant, and appends an SSE event only when `added + changed + removed > 0`, carried to other replicas over `NOTIFY`. Hints per deployment: a `WatchService` per directory locally (with overflow, a failed reset and an exhausted watch budget all requesting a reconcile); the git-sync sidecar's webhook in Kubernetes, with the checkout on a volume mounted read-only into the service and the commit hash read from the link target; a signed, deduplicated `push` webhook for a hosted repository, with a conditional request as the guarantee. A binding never implies watch-only. The intervals are engineering defaults to be tuned on data.

7. **The SPI keeps the snapshot as the baseline and adds, additively and pure JDK:** capabilities as data with an explicit unknown (`syncModes`, `deleteDetection`, `writeModes`, `exactlyOnce`, `cursorIsOrdered`, `spiVersion`); an opaque `Cursor` formatted by the connector, persisted by the host and handed back only once acknowledged; a sealed `Change` of `Read`, `Upserted` and `Deleted`, the last a tombstone; `Optional<BacklogSink> sink()` returned rather than inherited, with `WriteMode { UPSERT, INSERT_ONLY, UPDATE_ONLY, MIRROR }` diffed by the host against the last acknowledged sent image; and a `SyncReport` that separates `invalid` (the host's gate before any remote call) from `rejected` (the remote's own message). A snapshot captures its cursor before paginating; a change wins over an overlapping snapshot row; applying one change twice is a no-op by key and version; field mapping is host configuration, never connector code. **`SyncConnector` is retired as a separate seam**: a bidirectional connector is a `BacklogSource` whose `sink()` is present, selected by id like every source; the single-active resolution and the no-op fallback go.

8. **The agent surface sits inside the service, on the command layer the REST resources use, and only once that surface is authenticated and stable.** Tool annotations are untrusted hints and the protocol leaves access control to the server, so parity with the UI is an application-architecture property: every state change is a command in a module that depends on neither JAX-RS nor the MCP extension, fenced by an architecture test; the MCP endpoint is under the same OIDC configuration and audience as REST; an agent acting for a user carries the user's token and is recorded as actor, never principal; an autonomous agent is its own OAuth client with its own user record; mutating tools take an idempotency key honoured on every channel and the same `item.version` the UI sends; a read-only server variant and an identity-aware tool filter keep destructive tools unlisted without the scope; destructive and multi-item tools take `confirm`, `dryRun` and `maxItems`; the trace context is propagated so agent and human writes emit the same events. An agent's transition on a file-backed item enters the write-back loop of decision 2. The surface is not offered before sign-in (R-SEC-1) and the ratified `/api/v1` exist, because it must never be a way around the authenticated API.

## Consequences

- The import designed in VEC-53 gains an inventory, a last-good-row rule, visible divergence and gated pruning; its idempotence becomes a tested invariant rather than a property of one code path.
- A Vectis edit to a file-backed item is never settled until it is in the files. The client shows pending and conflicted states; a conflict record keeps both values and goes to a manual queue.
- The format's writer becomes public framework tooling with a sidecar mode and a base precondition on every mutating command; until it lands, write-back is off.
- Every CLI mutation, every UI write and every agent write share one version check. A stale command fails identically for a human and an agent.
- The schema gains the crosswalk columns and a command log; the registry drops `activeSyncConnector()`, the priority race and `NoopSyncConnector`, and `/api/extensions` lists sources with their capabilities.
- Staging runs the git-sync sidecar into a volume mounted read-only into the service, which settles how a native image sees `.vault/`.
- The MCP story waits on identity and the ratified API; when it comes, it is an in-process surface, not a second deployable.
- The engineering defaults (intervals, debounce, retry bounds) are recorded as choices to be tuned on data.

## Alternatives considered

- **Vectis as system of record, the files as an export.** Rejected: inverts the operating model's authority rule and puts the format's gate on the wrong side; the one tool that ran this loop documented stale-database overwrites, resurrected deletes and split-brain failures and abandoned it.
- **Newest-wins reconciliation between database and files.** Rejected for the same evidence.
- **Textual three-way merge of item files.** Rejected: hunk-level merges of adjacent YAML keys, moves between status directories read as delete plus add; the format's own rule for generated files is to regenerate, never hand-merge.
- **Wall-clock last-writer-wins per field.** Rejected: every product that documents it also documents the clock and ordering trouble; the only order is the backlog's commit sequence.
- **Canonical-wins on a both-changed field.** Proposed by the spike and withdrawn by the PO: it resolves a write-after-write hazard by discarding one write; the canonical answer is detect by version, refuse and replay.
- **A Java reimplementation of the format's writer.** Rejected: a second writer of a format whose only specification is the first writer.
- **A branch and pull request per edit.** Rejected for a backlog that lands on its main branch by policy; retained as an option for repositories that review backlog changes.
- **Vectis-side key allocation with a seeded counter**, and **hash or random ids**. Rejected: two allocators of one sequence, and the keys are the format's public, human-readable identity; the writer's serialised counter is the allocator.
- **A renumbering repair tool.** Rejected for now as over-engineering: prevention and detection exist; build it only if the manual repair is ever needed twice.
- **Watch-only binding without a timer.** Rejected: every documented event source is lossy.
- **Widening `SyncConnector` in place** and keeping its single-active resolution. Rejected: sources coexist, a no-op would have to invent an empty backlog, and nothing implements the stub.
- **A separate MCP server over the REST API.** Rejected: a second audience and deployable, audit that sees the server instead of the agent, parity by policy rather than by construction.
- **An MCP surface before the API is authenticated and stable.** Rejected by the PO: it must not be a way around the authenticated API.

## Reopen if

- A second file-backed source needs a writer that cannot be promoted to the public framework.
- The manual duplicate repair is needed twice, which is the trigger for a repair tool.
- A field needs an automatic resolution beyond refuse-and-replay, for example a counter that both sides increment.
- The reconcile defaults prove too slow or too costly on real data.
- An external tracker needs a conflict policy the ownership table cannot express.
